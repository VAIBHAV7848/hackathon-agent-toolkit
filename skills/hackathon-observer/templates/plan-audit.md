# Universal Adversarial Hackathon / Innovation Plan Audit

Apply only relevant checks for the actual event and project modality. Mark genuinely inapplicable checks `N/A`; do not create failures for missing features the event does not require. For each finding, include severity (blocker/high/medium/low), evidence or affected section, consequence, and a practical resolution. Do not report subjective preferences as defects.

## Challenge and evidence
- [ ] Official requirements, deliverables, deadline, and restrictions are captured.
- [ ] Every official criterion maps to planned behavior and proof.
- [ ] Claims distinguish fact, inference, assumption, and unresolved question.
- [ ] Sources are authoritative, relevant, current enough, and cited accurately.
- [ ] Prior-art research supports—not overstates—the differentiation claim.

## Product and feasibility
- [ ] Target user, root problem, and main workflow are clear.
- [ ] Minimum credible outcome is small enough for one primary builder and available time.
- [ ] P0 requirements have verifiable acceptance criteria.
- [ ] Critical unknowns have experiments, thresholds, owners, and fallbacks.
- [ ] Required materials/data/equipment/accounts/services are actually accessible or explicitly unresolved.

## Solution design and execution
- [ ] Technology choices fit skills, constraints, and deployment needs.
- [ ] The solution/design is not overcomplicated for the event and time available.
- [ ] Dependencies, integration order, estimates, and buffer are realistic.
- [ ] Task prompts are bounded and include scope, acceptance criteria, and stop conditions.
- [ ] A minimum demonstrable product and feature cut line are defined.

## Digital UI quality (only if a digital interface is in scope)
- [ ] UI visual direction is grounded in the product, audience, workflow, and any existing brand/design system.
- [ ] Default generic AI aesthetics (unmotivated dark/purple styling, gradients/glows, glassmorphism, repetitive card grids, fake metrics/testimonials, decorative clutter) are avoided unless explicitly justified and approved.
- [ ] Color, typography, spacing, layout, icons, imagery, and interaction patterns are consistent and purposeful.
- [ ] Functional controls, loading/empty/error/success states, responsive behavior, and accessibility checks are addressed as relevant.
- [ ] Actual rendered UI has been inspected at relevant viewports; if not, visual quality is marked unverified.

## Quality, security, and operation
- [ ] Appropriate validation covers normal, edge, failure, integration, repeatability, and regression cases as relevant.
- [ ] Security, privacy, licenses, and domain-specific obligations are addressed.
- [ ] AI/data claims use suitable evaluation methods when applicable.
- [ ] Setup, materials, secrets/data handling, diagnostics, delivery, and deployment where relevant are specified.
- [ ] Fallbacks exist for critical dependencies and demo failure.

## Presentation / submission integrity
- [ ] Demonstration or submitted artifact reflects the real project state.
- [ ] Mock, simulated, planned, and unimplemented behavior is labeled honestly.
- [ ] Metrics and impact claims have evidence and context.
- [ ] Presenters can explain the problem, workflow, differentiation, architecture, and limitations.
